# minihb 진행 노트

hibernate-build-v1 교재를 따라가며 채우는 노트다. 여기 적힌 것이 나중에 Q&A 답변의 재료가 된다.

가장 중요한 규칙: **내가 만든 것은 슬라이드에 올리지 않는다.** 슬라이드에 올라가는 근거는 예외 없이
hibernate-labs-v3(관측 문서)의 실습 1부터 5까지의 산출물이다.

중단 기준: **발표 D-7이 되면 구현을 멈춘다.** 진행 중인 단계가 있어도 멈춘다.

구현 결과가 대본과 어긋나면 대본을 고치기 전에 하이버네이트로 먼저 확인한다. 대본의 근거는 항상 하이버네이트다.

## 돌리는 법

| 명령 | 무엇을 돌리나 | Docker |
| --- | --- | --- |
| `./gradlew minihbTest` | minihb 단위 테스트 (벽 제외). 늘 초록이어야 한다 | 불필요 |
| `./gradlew wallTest` | 아직 못 넘은 벽. 빨간 게 정상이다 | 불필요 |
| `./gradlew test` | 전부. 관측 테스트 포함 | 필요 |

벽 테스트는 이렇게 표시한다. 단계 0의 실패 테스트 셋이 첫 사례다.

```java
@Tag("wall") // 단계 5에서 초록이 된다
@Test
void setMaxResults를_붙일_자리가_없다() { ... }
```

벽을 넘으면 `@Tag("wall")`을 지운다. 그러면 그 테스트가 `minihbTest`로 넘어오면서
"넘은 벽"과 "아직 못 넘은 벽"이 태스크로 갈린다.

## 커밋 규칙

단계마다 커밋하고, **막힌 상태를 반드시 커밋한다.** 벽에 부딪힌 커밋과 벽을 넘은 커밋 사이의 diff가
그대로 그 파트의 슬라이드 논리가 된다. 메시지는 단계 번호로 시작한다: `[5] postgres 렌더러 추가`

나중에 직접 쓰이는 diff 두 개를 기억해 둔다.

- 단계 5의 diff: PostgreSQL 렌더러를 추가하면서 건드린 파일 목록 (대본 4-3의 선을 어디에 그을지)
- 단계 7의 diff: CompiledQuery에 필드가 하나 늘어나는 커밋 (대본 6파트의 검증 자료)

## 회고 한 문장

단계를 끝낼 때마다 한 문장을 채운다. 빈칸으로 남겨두면 그 단계는 끝난 게 아니다.

- **단계 0**: 치환기가 처음 막힌 지점은 ____였고, 그 이유는 ____이다.
- **단계 1**: 파스 트리에 없어서 SQL을 못 만든 정보는 ____였다.
- **단계 2**: 구문 트리에 타입을 박기 위해 필요했던 것은 ____였다.
- **단계 3**: 빌더에서 타입 안전성을 지키려다 필요해진 것은 ____였다.
- **단계 4**: 메서드 이름을 쪼갤 때 메타모델이 필요했던 이유는 ____이다.
- **단계 5**: PostgreSQL을 추가하면서 건드린 파일은 ____개였고, QM은 ____.

- **단계 7**: 조립 계획을 실행 시점에 만들 수 없었던 이유는 ____이다.
- **단계 8**: UNION 결과에서 타입을 알 수 없어서 내가 한 일은 ____이다.

## 과제

태그: `구현` 만들어보면 답이 나온다 / `탐색` 하이버네이트 소스를 열어야 한다 /
`사고` 어디에도 적혀 있지 않다 / `내부` 대본으로 답할 수 있다

### B1 `구현` `사고` (단계 0)

단계 0의 치환기가 막힌 세 지점을 적고, 각각이 "구조가 없어서"인지 "정보가 없어서"인지 분류하라.
둘의 차이를 한 문장으로 정의할 것.

>

### B2 `구현` `사고` (단계 1)

단계 1의 구문 트리에 일부러 타입을 넣지 않았다. 만약 파싱하면서 바로 타입을 채웠다면 무엇이 문제가 되는가.
파싱과 의미 분석을 분리하는 이유를 자기 코드 기준으로 답하라.

>

### B3 `구현` (단계 2)

묵시적 조인을 어디에 저장하기로 했는가. 그 결정을 하이버네이트의 `SqmFrom` 구조와 비교하라.

>

### B4 `구현` `사고` (단계 2)

파라미터의 타입을 어떻게 결정했는가. 값이 들어오기 전에 타입을 아는 방법과, 그것이 불가능한 경우를 각각 적어라.

>

### B5 `구현` (단계 3, 관측 문서 Q2)

경로 A(문자열)와 경로 B(빌더)가 만든 QM이 완전히 같았는가. 달랐다면 골든 테스트 판정 기준으로 분류하라.

>

### B6 `구현` `사고` (단계 3, 관측 문서 Q3)

빌더를 "문자열을 만들어 파서에 넘기는" 방식으로 바꾸려면 무엇을 추가해야 하는가.
그렇게 늘어난 코드가 Hibernate 5가 치르던 비용이다. 줄 수와 위험 요소를 적어라.

>

### B7 `구현` `탐색` (단계 4, 관측 문서 Q1/Q16)

내 MethodNameParser는 빌더를 부르고, Spring Data JPA 4는 JPQL 문자열을 만든다.
두 설계를 문자열 파싱 비용과 플랜 캐시 적중 두 축으로 비교하고, 발표 2파트의 계단을 어느 쪽으로 그려야 하는지 결론을 내라.

>

### B8 `구현` (단계 5, 7)

단계 5에서 SQL 트리를 두기로 했는가 두지 않기로 했는가. 그 결정의 이유와, 단계 7에서 그 결정이 어떤 결과를 낳았는지 적어라.

>

### B9 `구현` (단계 5, 관측 문서 Q4)

PostgreSQL 렌더러를 추가하면서 건드린 파일 목록과 diff 크기를 적어라. 그 결과로 4-3에서 "이 예제에서 확인한 차이"로
말할 범위를 정하라. 진행 팁의 선("모든 DB 차이가 마지막 출력 단계에서만 발생한다고 일반화하지 않는다")은
내 구현으로 보면 어디에 그어지는가.

>

### B10 `구현` `사고` (단계 6, 관측 문서 Q3 후반)

단계 6에서 심은 버그를 고치는 데 IR 버전과 직통 버전이 각각 몇 군데를 건드려야 했는가.
이 수치가 M x N 대 M + N이라는 이론적 논증보다 강한 이유를 답하라.

>

### B11 `구현` `사고` (단계 7, 관측 문서 Q10)

조립 계획을 실행 시점에 만들 수 없었던 이유를 세 가지 적어라. 그리고 그 계획이 QM에 있어야 하는지,
SQL 트리에 있어야 하는지, 제3의 자리인지 자기 결정과 하이버네이트의 결정을 비교하라.

>

### B12 `구현` (단계 8, 관측 문서 Q7)

상속 전략을 바꿀 때 QM을 건드려야 했는가. 건드렸다면 어디를, 왜인가.
그 사실이 "SQM에서는 SlotClaim을 조회 대상으로 표현합니다"를 무효로 만드는가.

>

### B13 `구현` `사고` (단계 8, 관측 문서 Q8)

UNION에 상수 컬럼을 넣게 된 경위를 순서대로 서술하고, 그것이 태그된 유니온의 태그인지 vtable 포인터인지
RTTI인지 판정하라. 셋의 차이를 먼저 정의할 것.

>

### B14 `사고` (단계 8)

SINGLE_TABLE의 판별 컬럼과 TABLE_PER_CLASS의 상수 컬럼은 같은 장치인가.
하나는 저장되어 있고 하나는 쿼리 시점에 만들어진다는 점을 근거로 답하라.

>

### B15 `구현` `탐색` (단계 9, 관측 문서 Q16)

빌더 경로의 캐시 키를 무엇으로 하기로 했는가. 예측과 하이버네이트의 실제 구현이 같았는가.

>

### B16 `구현` `사고` (골든 테스트)

골든 테스트에서 하이버네이트와 갈라진 지점을 전부 나열하고, 각각을 의미와 표기로 분류하라.
의미로 분류된 것에 대해 하이버네이트가 그렇게 하는 이유를 한 문장씩 적어라.

>

### B17 `사고` (전체)

이 구현에서 내가 만들지 않기로 한 것을 세 개 적고, 하이버네이트가 그것을 만든 이유를 각각 답하라.
힌트: 더티 체킹, flush 순서 결정, 2차 캐시.

>

## 체크리스트

### 구현이 끝났다고 판단하는 기준

- [ ] 단계 0의 실패 테스트 세 개가 전부 초록이다
- [ ] 경로 A와 경로 B가 같은 QM을 만든다는 테스트가 초록이다
- [ ] MethodNameParser가 hql 패키지를 import하지 않는다
- [ ] 같은 QM에서 MySQL SQL과 PostgreSQL SQL이 둘 다 나온다
- [ ] 상속 전략 세 개에서 QM이 동일하다
- [ ] CompiledQuery가 SQL 말고 조립 계획도 들고 있다
- [ ] 골든 테스트 열 개 중 몇 개가 통과하는지 숫자로 안다
- [ ] 회고 한 문장이 단계마다 적혀 있다

### 발표 준비로 넘어가기 전 확인

- [ ] 관측 문서의 실습 2와 4는 하이버네이트에서 직접 찍었다
- [ ] 슬라이드에 내 코드가 한 줄도 없다
- [ ] 구현 결과와 대본이 어긋나는 지점을 하이버네이트로 재확인했다
- [ ] 본인 Spring Data 버전에서 메서드 이름 경로의 합류 지점을 스택 트레이스로 확인했다 (4.x라면 계단 그림을 고쳤다)
- [ ] Q&A 총알 중 이 과제로 답이 바뀐 것을 표시해뒀다 (상수 컬럼, EAGER N+1, Criteria 캐싱, DomainResult, Spring Data 4의 문자열 경로)
- [ ] D-7이 지났으면 구현을 멈췄다

### 발표 당일에 쓰지 말아야 할 말

- "제가 직접 만들어봤는데요" (Q&A에서 근거가 필요할 때만. 발표 본문에서는 쓰지 않는다)
- "이건 제 구현 기준입니다" (근거가 흔들린다. 하이버네이트 기준으로만 말한다)
